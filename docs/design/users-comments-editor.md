# Дизайн: пользователи, комментарии, редактор постов

Статус: черновик на обсуждение. Кода пока нет.

Три задачи, которые здесь спроектированы:
1. Система пользователей: админ (один), читатели (с аккаунтом), гости (без аккаунта).
2. Комментарии к постам и рецептам, с приватными и публичными.
3. Блочный редактор постов с правкой на месте + отдельный админ-раздел.

## Что уже решено

| Вопрос | Решение |
| --- | --- |
| Как читатели получают аккаунт | Открытая регистрация с подтверждением email |
| Редактор | Правка на месте: блок выглядит как на сайте, кликаешь и печатаешь |
| Модерация | Комментарий виден сразу, админ может скрыть/удалить |
| Комментарии дополнительно | Ответы (1 уровень), комментарии к рецептам, уведомления на почту, правка своего комментария |

Из этого следует, что **отправка почты нужна обязательно** — и для подтверждения адреса, и для
сброса пароля, и для уведомлений. Одна зависимость закрывает все три.

## Почему остаёмся на SQLite

Обсуждалось: не перейти ли на Postgres ради «нормальной авторизации». Не переходим, потому что:

- **Время жизни сессии не зависит от движка БД.** 30 дней с продлением делается одинаково на обоих.
  Важно другое: сессии лежат в таблице, а не в памяти процесса — иначе каждый автодеплой
  разлогинивал бы всех.
- **Главное ограничение Postgres не снимает.** `middleware.ts` работает на Edge-рантайме, где
  недоступен ни `better-sqlite3`, ни обычный TCP-клиент Postgres. Схема «оптимистичная проверка в
  middleware + авторитетная проверка в слое данных» нужна в любом случае.
- **Цена перехода реальна:** второй контейнер на домашнем ноуте, `pg_dump` вместо копирования
  одного файла (вся система бэкапов построена вокруг файла), миграция контента, пул соединений.
- **Выигрыш — нет.** Параллельная запись при одном авторе и десятке комментаторов не нужна;
  SQLite в WAL не блокирует читателей, вставка комментария занимает миллисекунды.

Пересмотреть стоит, если появится второй автор, который пишет одновременно, или если понадобится
запускать несколько инстансов приложения. Переезд из Drizzle — смена диалекта и переписывание
миграций, примерно день.

## 1. Роли и доступ

Три роли, но в базе хранятся две (гость — это просто отсутствие сессии).

| | Читать посты | Комментировать | Приватный комментарий | Модерация | Писать посты |
| --- | --- | --- | --- | --- | --- |
| Гость | да | нет | нет | нет | нет |
| Читатель (`reader`) | да | да, после подтверждения почты | да | свои: правка 15 мин, удаление | нет |
| Админ (`admin`) | да | да | да | всё | да |

Админ ровно один — это ты. Отдельной роли «редактор» не делаем: её некому занять, а каждая лишняя
роль это ветвление в каждой проверке прав.

**Как проверяются права.** Два уровня, и это не дублирование, а разные задачи:

- `middleware.ts` — дешёвый оптимистичный гейт: есть ли вообще кука сессии. Нет — редирект на
  `/login`. Ничего больше он знать не может (Edge-рантайм, доступа к БД нет).
- Слой данных — авторитетная проверка. Функция `getCurrentUser()` читает сессию из БД и возвращает
  пользователя с актуальной ролью. Её вызывает каждый server action и каждая страница, где личность
  важна. Заблокированный или удалённый пользователь останавливается здесь, немедленно, без ожидания
  истечения куки.

Из этого следует правило, которое легко нарушить по невнимательности: **middleware никогда не
является единственной защитой**. Если страница или action доступны только админу, проверка живёт
внутри них.

## 2. Пользователи и сессии

### `users`

| Поле | Тип | Комментарий |
| --- | --- | --- |
| `id` | integer pk | |
| `email` | text unique not null | хранится в нижнем регистре, обрезанный |
| `displayName` | text not null | то, что видно под комментарием |
| `passwordHash` | text not null | формат ниже |
| `role` | text not null | `admin` \| `reader`, по умолчанию `reader` |
| `emailVerifiedAt` | integer null | null = не подтверждён |
| `blockedAt` | integer null | бан читателя, без удаления его комментариев |
| `notifyOnReply` | integer not null | 1/0, слать ли письмо при ответе на его комментарий |
| `createdAt` / `updatedAt` | integer not null | unix-секунды, как везде в проекте |

`displayName` не уникален — два «Ани» это нормально, они различаются по контексту, а не по нику.
Email не показывается публично **никогда** и не попадает ни в одну публичную выдачу.

**Хеширование пароля:** `scrypt` из `node:crypto`, со случайной солью на каждого пользователя.
Новых зависимостей не требует (`bcrypt`/`argon2` — нативные модули, а мы уже намучились с
`better-sqlite3` в Docker). Формат хранения: `scrypt$<N>$<r>$<p>$<salt_b64>$<hash_b64>` — параметры
внутри строки, чтобы их можно было поднять потом без слома старых хешей. Сравнение —
`timingSafeEqual`. Текущая схема (`scryptSync(password, SESSION_SECRET)`, соль общая на всех) уходит.

**Как мигрирует твой админский аккаунт.** Сейчас вход — это `ADMIN_PASSWORD` из окружения, без
всякой строки в базе. План: скрипт `scripts/create-admin.mjs`, который берёт `ADMIN_EMAIL` и
`ADMIN_PASSWORD` из окружения и создаёт (или обновляет) пользователя с ролью `admin` и уже
подтверждённой почтой. Запускается один раз: `docker compose exec app node scripts/create-admin.mjs`.
После этого `ADMIN_PASSWORD` остаётся в `.env` только как аварийный способ пересоздать доступ.

### `sessions`

| Поле | Тип | Комментарий |
| --- | --- | --- |
| `id` | text pk | 32 случайных байта, base64url — это и есть значение куки |
| `userId` | integer not null | FK → `users.id`, `on delete cascade` |
| `createdAt` | integer not null | |
| `expiresAt` | integer not null | |
| `lastSeenAt` | integer not null | |

Непрозрачный идентификатор, а не JWT. Причина: роль и статус бана всегда свежие (читаются из
`users` при каждой проверке), сессию можно отозвать, и есть «выйти на всех устройствах». JWT дал бы
возможность проверять роль прямо в middleware, но ценой протухших данных в токене — а раз
авторитетная проверка всё равно в слое данных, эта возможность не нужна.

**Время жизни.** Кука `greendal_session`: `httpOnly`, `sameSite=lax`, `secure` в проде, `path=/`,
`maxAge` 30 дней. Скользящее продление: если сессии больше суток от последнего продления, при
очередном запросе `expiresAt` и `lastSeenAt` двигаются вперёд. То есть активный читатель не
разлогинивается никогда, неактивный — через 30 дней. Запись в БД при этом происходит не чаще раза в
сутки на сессию, а не на каждый запрос.

Сессия пересоздаётся (старая удаляется, новая выдаётся) при входе и при смене пароля. Сброс пароля
убивает **все** сессии пользователя.

### `auth_tokens`

Одна таблица на подтверждение почты и на сброс пароля.

| Поле | Тип | Комментарий |
| --- | --- | --- |
| `id` | integer pk | |
| `userId` | integer not null | FK → `users.id`, cascade |
| `purpose` | text not null | `verify_email` \| `reset_password` |
| `tokenHash` | text not null | SHA-256 от токена; сам токен в базе не лежит |
| `expiresAt` | integer not null | подтверждение 48 ч, сброс 1 ч |
| `usedAt` | integer null | одноразовость |
| `createdAt` | integer not null | |

Токен хранится только хешем: утечка базы не даёт захватить аккаунты.

### Сценарии

**Регистрация.** Форма: имя, email, пароль (минимум 10 символов), плюс скрытое поле-ловушка для
ботов. Создаётся неподтверждённый пользователь, уходит письмо со ссылкой `/verify?token=…`. Человек
залогинен сразу, но до подтверждения **не может комментировать** — вместо формы видит «подтверди
почту» и кнопку «отправить письмо ещё раз». Без этого барьера бот регистрируется на несуществующий
адрес и спамит.

**Вход.** Email + пароль. Сообщение об ошибке одинаковое для «нет такого адреса» и «неверный
пароль» — иначе форма превращается в проверялку «а зарегистрирован ли тут вот этот человек».

**Забыл пароль.** `/forgot` → всегда отвечает «если такой адрес у нас есть, письмо отправлено»,
независимо от того, есть он или нет (та же причина). Письмо → `/reset?token=…` → новый пароль →
все сессии этого пользователя убиваются, выдаётся новая.

**Смена email** в первой версии не делаем: это отдельный флоу с подтверждением нового адреса и
защитой старого. Если понадобится — допишем.

**Удаление аккаунта** читателем: в `/account`. Комментарии при этом не исчезают (иначе у чужих
веток образуются дыры), а превращаются в «удалённый читатель» — `authorId` обнуляется, имя больше
не хранится. Это осознанный компромисс; альтернатива — удалять вместе с комментариями — тоже
допустима, скажи, если хочешь так.

## 3. Почта

Модуль `src/lib/email.ts` с единственной функцией `sendEmail({ to, subject, text, html })` и
транспортом, выбираемым по `EMAIL_PROVIDER`:

- `console` — для локальной разработки: письмо печатается в лог вместе со ссылкой подтверждения.
  Обязательно, иначе локально невозможно зарегистрироваться.
- `resend` — HTTP API, один `fetch`, новых npm-зависимостей не требует.
- `smtp` — на случай, если захочется свой сервер; тянет `nodemailer`.

**Рекомендую Resend.** Причины: это HTTP, а не SMTP (домашние провайдеры любят резать исходящие
25/587), бесплатный тариф покрывает такой блог с огромным запасом, и DNS-записи ложатся в зону
Cloudflare, которая у тебя уже настроена под туннель.

Что нужно один раз сделать руками: завести аккаунт, добавить домен, прописать в Cloudflare DNS
записи SPF и DKIM, которые он выдаст (TXT-записи, проксирование к ним не применяется), желательно
ещё DMARC. Без этого письма уедут в спам. Отправитель — `no-reply@<твой домен>`; в уведомлениях о
комментариях ставим `Reply-To` на твой настоящий адрес, чтобы можно было ответить прямо из почты.

Письма, которые шлёт сайт:

| Письмо | Кому | Когда |
| --- | --- | --- |
| Подтверждение адреса | читателю | регистрация, повторный запрос |
| Сброс пароля | читателю | запрос на `/forgot` |
| Новый комментарий | тебе | кто-то прокомментировал; в теме помечено, если приватный |
| Ответ на твой комментарий | читателю | ты ответила, и у него включено `notifyOnReply` |

Первые два — транзакционные, от них нельзя отписаться. Последние два — уведомления, в каждом ссылка
на `/account`, где тумблер.

**Отказ почты не ломает основное действие.** Если провайдер лежит, регистрация всё равно проходит
(пользователь создан, показываем «письмо не ушло, попробуй запросить заново»), а комментарий всё
равно публикуется. Уведомления отправляются без `await`, с `catch` и записью в лог — задержка
почтового API не должна тормозить отправку комментария.

## 4. Комментарии

### `comments`

| Поле | Тип | Комментарий |
| --- | --- | --- |
| `id` | integer pk | |
| `postId` | integer null | FK → `posts.id`, cascade |
| `recipeId` | integer null | FK → `recipes.id`, cascade |
| `authorId` | integer null | FK → `users.id`; null = удалённый читатель |
| `parentId` | integer null | FK → `comments.id`; null = верхний уровень |
| `body` | text not null | обычный текст, не HTML (см. ниже) |
| `visibility` | text not null | `public` \| `private`, по умолчанию `public` |
| `status` | text not null | `visible` \| `hidden` \| `deleted` |
| `createdAt` / `updatedAt` | integer not null | |
| `editedAt` | integer null | |

Ровно одно из `postId` / `recipeId` заполнено — это закрепляется `CHECK`-констрейнтом. Вариант с
одной парой «тип + id» был бы короче, но потерял бы целостность: при удалении поста его комментарии
не удалились бы сами. `PRAGMA foreign_keys = ON` в проекте уже стоит, так что каскад сработает.

Индексы: `(postId, createdAt)`, `(recipeId, createdAt)`, `(authorId)`, `(parentId)`.

### Правила видимости

Это самая тонкая часть, поэтому формулирую как функцию.

```
видно(зритель, комментарий):
  status != visible        → только админ
  visibility == public     → всем
  visibility == private    → админ,
                             ИЛИ автор комментария,
                             ИЛИ автор родительского комментария
```

Последнее условие важно: оно делает возможным «тихий личный ответ». Ты отвечаешь приватно на
публичный комментарий читателя — читатель ответ видит, остальные нет.

Следствия, которые стоит проговорить:

- **Автор всегда видит собственный комментарий**, даже если ты его скрыла. Прятать от человека его
  же слова — так себе поведение; вместо этого он видит пометку «скрыт с публичной страницы».
- **Ответ на приватный комментарий обязан быть приватным.** Иначе публичный ответ раскрывает
  содержание и сам факт приватного сообщения. Это принудительно, а не галочкой.
- **Счётчик комментариев считает только видимое зрителю.** Иначе «12 комментариев» под постом, где
  публичных три, выдаёт существование девяти приватных.
- Приватные комментарии не попадают в RSS, в OG-теги и вообще никуда, кроме страницы.

### Кто может менять видимость

Ты просила уметь и то, и другое, но здесь я хочу обозначить проблему, прежде чем делать.

`public → private` (ты прячешь чужой публичный комментарий) — нормально, это модерация.

`private → public` (ты публикуешь чужой приватный комментарий) — **предлагаю запретить**. Человек
написал в расчёте на то, что это между вами; публиковать это односторонним решением — ровно то, за
что не любят соцсети. Технически ничего не мешает, вопрос только в том, хочешь ли ты такую кнопку.
Варианты:

- **(рекомендую)** Запретить совсем для чужих комментариев. Свои приватные ты, конечно, публикуешь
  свободно. Хочешь опубликовать чужое — спроси автора, он сам переключит.
- Разрешить, но с диалогом «автор писал это приватно, точно опубликовать?».

Скажи, какой вариант — от этого зависит только текст подтверждения и одна проверка прав.

### Правка и удаление

- Читатель правит свой комментарий 15 минут после отправки, потом он замораживается. Пометку
  «изменено» не показываем: за 15 минут его, скорее всего, никто не успел прочитать, а шум в
  интерфейсе появляется на каждом исправленном опечатке.
- Читатель может удалить свой комментарий в любой момент. Если на нём висят ответы — остаётся
  надгробие «комментарий удалён», чтобы ветка не разваливалась; если нет — исчезает целиком.
- Ты можешь скрыть (`hidden`) или удалить (`deleted`) любой. Скрытие обратимо, удаление нет.
- Чужие комментарии ты **не редактируешь** — такой кнопки не будет вообще. Править чужие слова от их
  имени нельзя, даже в своём блоге.

### Как рендерится текст комментария

Сейчас `renderMarkdown` намеренно не санитизируется — в README это объяснено тем, что автор один.
С появлением читателей это перестаёт быть правдой, и это **настоящая дыра XSS**, а не теоретическая.

Инвариант, который вводим: **HTML доверяем только контенту, написанному админом. Всё, что напечатал
читатель, экранируется.**

Для комментариев в первой версии — вообще без markdown: обычный текст, переносы строк сохраняются
(`white-space: pre-wrap`), ссылки распознаются автоматически и получают
`rel="nofollow ugc noopener"`. Никакого HTML, ноль поверхности атаки. Ограничение длины — 4000
символов.

Если потом захочется жирный/курсив в комментариях, это апгрейд до ограниченного подмножества
markdown плюс санитайзер (`sanitize-html` или `DOMPurify`) — отдельная задача с новой зависимостью.

### Антиспам

Регистрация с подтверждением почты + ограничение частоты + ловушка в форме регистрации. Плюс
таблица `rate_limits` (`key`, `count`, `resetAt`) для лимитов: попытки входа, регистрации, запросы
письма, отправка комментариев.

**Важная деталь про IP.** Сайт стоит за Cloudflare Tunnel, поэтому настоящий адрес клиента приходит
в заголовке `CF-Connecting-IP`. Если брать адрес соединения, все запросы будут выглядеть как один
клиент, и первый же лимит по IP заблокирует вообще всех.

## 5. Редактор постов

### Хранение

У `posts` появляется колонка `blocks` (TEXT, JSON) — ровно тем же приёмом, каким рецепты уже хранят
`ingredients` и `steps`, так что это не новый паттерн для проекта.

```ts
type Block =
  | { id: string; type: 'text';    markdown: string }
  | { id: string; type: 'image';   url: string; alt: string; caption?: string;
                                   width?: 'column' | 'wide' | 'full' }
  | { id: string; type: 'divider'; style?: 'rule' | 'squiggle' | 'dots' }
  | { id: string; type: 'ps';      text: string; recipeId?: number | null };
```

- `id` — короткая случайная строка, стабильная между сохранениями: нужна как ключ React и как
  идентификатор при перетаскивании.
- Внутри текстового блока — по-прежнему markdown (`**жирный**`, `_курсив_`, `>` цитата, `##`
  подзаголовок, списки, ссылки). Ты уже им пользуешься, а блоки отвечают за структуру, не за
  форматирование внутри абзаца.
- `width` у картинки: `column` — по ширине текста (по умолчанию), `wide` — шире колонки,
  `full` — во всю ширину экрана. У сайта узкая мера набора (`--measure: 34rem`), и фотография
  во всю ширину — заметный визуальный приём, ради которого стоит держать этот переключатель.
- `ps` — обобщение того, что уже есть: сейчас это `psRecipeId` + `psText`, намертво прибитые к
  подвалу поста. Становится блоком, который можно поставить где угодно, с той же опциональной
  ссылкой на рецепт.

### Миграция существующих постов

Осторожно, потому что один раз контент уже потерялся.

1. Миграция добавляет колонку `blocks` (nullable). Ничего не удаляет.
2. Отдельный скрипт оборачивает каждый существующий `body` в один текстовый блок; если у поста были
   `psRecipeId`/`psText` — добавляет в конец `ps`-блок.
3. Старые колонки `body`, `psRecipeId`, `psText` **остаются на месте**. Рендер использует `blocks`,
   если они не пусты, иначе падает обратно на `body`.
4. Только после того, как ты своими глазами подтвердишь, что все посты выглядят правильно, отдельной
   миграцией дропаем старые колонки. Можно и не дропать вообще — пара неиспользуемых колонок дешевле
   любого риска.

Побочные места, которые завязаны на `body` и их придётся перевести на блоки: `readingTime()` в
`format.ts` и генерация `feed.xml`.

### Как выглядит правка на месте

Страница редактора рисует пост **теми же стилями, что и сайт** — та же бумага, та же гарнитура, та
же ширина колонки, тот же `.prose`. Элементы управления появляются поверх, по наведению.

**Заголовок и подзаголовок.** Прямо на месте: `<textarea>` с авторостом, стилизованный точь-в-точь
как `h1` на странице поста, под ним — строка тизера (`dek`) более светлым. Это настоящие поля формы,
а не `contenteditable` — доступность и предсказуемость важнее, а выглядит одинаково.

**Блоки.**

| Тип | Как выглядит в редакторе |
| --- | --- |
| текст | `<textarea>` с авторостом, шрифт и межстрочный как в `.prose` — текст стоит ровно там, где окажется на странице. Разметка markdown видна как есть, во время набора |
| картинка | Сама картинка в своей реальной ширине, поле подписи под ней. Пустое состояние — пунктирная зона «перетащи картинку или нажми» |
| разделитель | Настоящий разделитель; клик переключает стиль (линейка → загогулина → точки) |
| пс | Настоящая плашка «ps» с редактируемым текстом и выпадашкой выбора рецепта |

**Управление блоком** — по наведению, слева ручка для перетаскивания, справа «⋯» с меню: вверх,
вниз, дублировать, удалить, плюс специфичное для типа (ширина картинки, стиль разделителя).

**Вставка блока** — кнопка «+» в промежутке между блоками (проявляется при наведении) и в конце
документа. Меню: текст / картинка / разделитель / пс. Дополнительно: `/` в начале пустого
текстового блока открывает то же меню, как в Notion — приятно, но необязательно, можно отложить.

**Клавиатура.**

| Сочетание | Действие |
| --- | --- |
| `Enter` | перенос строки внутри текстового блока (пустая строка = новый абзац markdown) |
| `Cmd/Ctrl+Enter` | новый текстовый блок ниже |
| `Backspace` в начале пустого блока | удалить блок, курсор в конец предыдущего |
| `Cmd/Ctrl+S` | сохранить |

**Перетаскивание.** Для «конструктора» это ожидаемо, но HTML5 drag-and-drop руками — источник боли.
Предлагаю `@dnd-kit/core` (новая зависимость, ~10 КБ, без перетаскивания всё равно остаются
стрелки в меню). Если не хочешь новых зависимостей — делаем только стрелки, а перетаскивание
добавим позже.

**Картинки.** Загрузка перетаскиванием файла на блок, вставкой из буфера обмена, или через файловый
диалог. Ходит в существующий `/api/upload`. Отдельно: сейчас картинки **не сжимаются** (лимит 8 МБ и
всё), и это означает, что фотография с телефона уедет читателю целиком, через домашний канал и
туннель. Рекомендую добавить `sharp` и уменьшать при загрузке до разумной ширины. Это тоже новая
зависимость, но в README она уже помечена как «добавь, если начнёшь кидать фотки с телефона».

**Сохранность черновика** — отдельно, потому что терять текст обиднее всего:

- Явное сохранение кнопкой и `Cmd+S`.
- Автосохранение на сервер раз в ~20 секунд, если есть несохранённые изменения (статус `draft` в
  постах уже есть).
- Дополнительно копия в `localStorage` браузера. Если вкладка умерла, при следующем открытии —
  плашка «есть несохранённая версия от 14:32, восстановить?».
- Предупреждение браузера при попытке закрыть вкладку с несохранёнными изменениями.

**Режим «как у читателя»** — одна кнопка, прячет всю редакторскую обвязку, чтобы посмотреть на
результат без подсказок и ручек.

**Нижняя панель** (липкая): черновик/опубликовано, дата публикации, «Сохранить», «Открыть на сайте»,
«Удалить».

**Телефон.** Предполагаю, что длинные посты ты пишешь не с телефона, поэтому цель скромная: редактор
не разваливается и позволяет поправить опечатку. Две колонки и ховер-контролы на узком экране
заменяются на «тап по блоку → панель действий снизу».

## 6. Админ-раздел

Сейчас `/admin` — плоский список всего. Становится так:

| Страница | Что на ней |
| --- | --- |
| `/admin` | Сводка: черновики, новые комментарии (со счётчиком), последняя активность, кнопка «написать» |
| `/admin/thoughts` | Таблица постов: заголовок, статус, дата, число комментариев, действия. Фильтр черновики/опубликованные, поиск по заголовку |
| `/admin/recipes` | То же для рецептов |
| `/admin/comments` | Лента всех комментариев, новые сверху. Фильтры: все / приватные / к постам / к рецептам. У каждого — ответить (прямо тут), скрыть, удалить |
| `/admin/readers` | Кто зарегистрировался: имя, почта, подтверждён ли, сколько комментариев, когда пришёл. Действия: заблокировать, разблокировать, удалить |
| `/admin/settings` | Существующие тексты сайта |

Приватные комментарии в ленте помечены отдельно и по умолчанию выведены наверх — по смыслу это
письма тебе, а не модерация.

**Удаление всегда с подтверждением, и подтверждение называет последствия.** Не «удалить пост?», а
«Удалить «a small case for boring weeks»? Вместе с ним удалятся 4 комментария». Каскад по внешнему
ключу сработает молча, поэтому про него должен сказать интерфейс.

Вся админка помечена `robots: noindex` (уже так) — то же самое нужно для `/account`, `/login`,
`/register` и прочих служебных страниц.

## 7. Публичные страницы

**Новые страницы:** `/register`, `/login`, `/forgot`, `/reset`, `/verify`, `/account`.
`/admin/login` переезжает на общий `/login`, который после входа отправляет админа на `/admin`, а
читателя — туда, откуда он пришёл.

**Шапка.** Для гостя — ссылка «войти». Для читателя — имя и «выйти». Для тебя — ещё и «стол»
(ссылка на админку).

**Блок комментариев** внизу поста и рецепта:

- гость видит публичные комментарии и приглашение «войди или заведи аккаунт, чтобы написать»;
- читатель видит публичные + свои приватные + адресованные ему приватные ответы, и форму с галочкой
  «только для автора блога»;
- ты видишь всё, с кнопками модерации прямо в ленте.

**Язык интерфейса.** Сайт написан строчными буквами и тёплым тоном («come in, take your shoes off»).
Новые элементы держатся того же: «войти», «оставить письмо», «только для автора». Заголовок секции
комментариев — рукописным шрифтом (`.hand`, Orange Juice), как «thoughts» и «recipes», через
существующий `.sectionMark`.

## 8. Безопасность: сводный чеклист

- HTML только из контента, написанного админом. Всё, что напечатал читатель, экранируется.
- `scrypt` с индивидуальной солью, сравнение `timingSafeEqual`.
- Одинаковые сообщения об ошибках на входе и на `/forgot` — не даём проверять, кто зарегистрирован.
- Токены подтверждения и сброса хранятся хешами, одноразовые, с истечением.
- Кука сессии `httpOnly` + `sameSite=lax` + `secure` в проде. Пересоздание сессии при входе и смене
  пароля; сброс пароля убивает все сессии.
- Лимиты частоты по настоящему IP из `CF-Connecting-IP`.
- Комментировать можно только с подтверждённой почтой.
- Ограничение длины: комментарий 4000 символов, имя 60 и без переносов строк.
- Приватные комментарии не утекают ни через счётчики, ни через RSS, ни через OG-теги.
- Загрузка файлов остаётся привилегией админа — читатели картинки не грузят.
- CSRF: server actions в Next проверяют origin сами; полагаемся на это, ручных форм с `fetch` к
  мутирующим эндпоинтам не делаем.

## 9. Миграции и порядок выкатки

Новые таблицы: `users`, `sessions`, `auth_tokens`, `comments`, `rate_limits`.
Изменения: `posts.blocks` (новая nullable-колонка).

Всё — через `npm run db:generate`, с чтением сгенерированного SQL перед коммитом, по процессу,
который мы только что завели.

Три фазы, каждая — отдельный PR, каждая выкатывается самостоятельно и не ломает сайт:

**Фаза 1 — пользователи.** Таблицы `users`/`sessions`/`auth_tokens`/`rate_limits`, модуль почты,
страницы входа/регистрации/сброса, `getCurrentUser()`, перевод админки на новую авторизацию, скрипт
создания админа. Комментариев ещё нет — то есть видимых изменений для читателя почти никаких, кроме
возможности завести аккаунт. Это хорошо: самый рискованный кусок выкатывается отдельно.

**Фаза 2 — комментарии.** Таблица, правила видимости, лента на страницах поста и рецепта, раздел
модерации, уведомления на почту.

**Фаза 3 — редактор.** Колонка `blocks`, рендер блоков на публичной стороне, редактор с правкой на
месте, перенос существующих постов в блоки, перестройка админ-раздела.

Порядок не случаен: фаза 2 опирается на фазу 1, а фаза 3 ни от чего не зависит и может подождать,
пока первые две устоятся.

## 10. Открытые вопросы

1. **`private → public` для чужих комментариев** — запретить (рекомендую) или разрешить с
   предупреждением?
2. **Перетаскивание блоков** — берём `@dnd-kit` или пока обходимся стрелками?
3. **Сжатие картинок при загрузке** (`sharp`) — добавляем сразу или живём с восьмимегабайтными
   фотографиями?
4. **Заголовок отдельным типом блока** или достаточно `##` внутри текстового?
5. **Удаление аккаунта читателем**: комментарии остаются обезличенными (рекомендую) или удаляются
   вместе с ним?
6. **Адрес отправителя** — какой домен/ящик использовать для писем и готова ли ты добавить
   SPF/DKIM-записи в Cloudflare?
7. **Приватные комментарии отдельным разделом** («письма») или достаточно фильтра в общей ленте?
